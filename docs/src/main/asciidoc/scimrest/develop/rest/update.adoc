= Update script

How to implement update operations in a SCIMREST connector using PATCH or PUT, including multi-endpoint scenarios and attribute-specific endpoint routing.

== Basic update script using PATCH

The simplest update script (heavily using defaults) for the `User` object class, where the REST API provides a PATCH operation, could look like this:

[source,groovy]
----
objectClass("User") {
    update {
        endpoint(PATCH, "/users/{id}") {
            request {
                contentType APPLICATION_JSON
            }
        }
    }
}
----

Where:
* This simplest script heavily relies on default behavior of connector framework.

* The `endpoint` method specifies the endpoint to be used for
   update operation. In this case we use path parameter `{id}` which
   will be replaced with the UID of the object being updated.
* The `httpOperation` is set to `PATCH`, so the update is a partial update of the object.
* The `request` block allows to customize the request. In this case
   we specify that the content type of the request is JSON.
   `queryParameter(name, value)` adds a static query parameter to the request URL.
** If no body `implementation` is specified, the default implementation
    will be used which will serialize only changed `updateable` attributes from the `objectClass` into JSON body.

The same update in YAML:

[source,yaml]
----
objectClasses:
  User:
    update:
      endpoints:
        - method: PATCH
          path: /users/{id}
          request:
            contentType: application/json
----

See declarative YAML for the full reference.

== Basic update script using PUT

[source,groovy]
----
objectClass("User") {
    update {
        endpoint(PUT, "/users/{id}") {
            request {
                contentType APPLICATION_JSON
            }
        }
    }
}
----

Where:

* This simplest script heavily relies on default behavior of connector framework.
* The `endpoint` method specifies the endpoint to be used for
   update operation. In this case we use path parameter `{id}` which
   will be replaced with the UID of the object being updated.
* The `httpOperation` is set to `PUT`, so the update replaces the object.
** The `request` block allows to customize the request. In this case
   we specify that the content type of the request is JSON.
   `queryParameter(name, value)` adds a static query parameter to the request URL.
** If no body `implementation` is specified, the default implementation serializes the changed attributes (deltas applied on top of the original values) into the JSON body.
** The framework reads the original state when necessary to apply the deltas.

== Limiting update to a supported subset of attributes

By default, an endpoint handles all `updateable` attributes of the object class. When the server accepts only part of them in the update request, `supportedAttributes` narrows the set the endpoint handles — deltas for attributes covered by no endpoint make the update fail with `ConnectorException` ("Unsupported attributes"):

[source,groovy]
----
objectClass("User") {
    update {
        endpoint(PATCH, "/users/{id}") {
            // only these attributes are accepted in the PATCH body
            supportedAttributes "externalId", "displayName", "nickName", "email"
            request {
                contentType APPLICATION_JSON
            }
        }
    }
}
----

The same in YAML:

[source,yaml]
----
objectClasses:
  User:
    update:
      endpoints:
        - method: PATCH
          path: /users/{id}
          request:
            contentType: application/json
          supportedAttributes:
            - externalId
            - displayName
            - nickName
            - email
----

A `supportedAttribute(name)` block with `value(...)` further restricts an attribute to specific values — the endpoint is selected only when the delta values match (see the activation / locking example below).

NOTE: `supportedAttribute(name) { transition(from, to) }` is accepted by the DSL, but value-transition filtering is *not enforced yet* — a transition-only endpoint does not handle the attribute.

== Memberships stored as separate records

Some REST APIs store each relationship as a separate record with its own identifier.
Use `relationshipRecords` when updating a membership attribute must create or delete these records.
The membership attribute must already exist in the schema and be multivalued.

[source,groovy]
----
objectClass("User") {
    update {
        relationshipRecords("groups") {
            endpoint "/memberships"
            sourceField "userId"
            targetField "groupId"
            idField "id"
        }
    }
}
----

The equivalent YAML is:

[source,yaml]
----
objectClasses:
  User:
    update:
      relationshipRecords:
        groups:
          endpoint: /memberships
          sourceField: userId
          targetField: groupId
          idField: id
----

For user `U`, assume `GET /memberships` returns:

[source,json]
----
[
  {"id": "M1", "userId": "U", "groupId": "A"},
  {"id": "M2", "userId": "U", "groupId": "B"},
  {"id": "M3", "userId": "V", "groupId": "A"}
]
----

Replacing `User.groups` with `[B, C]` deletes `/memberships/M1`, retains `M2`, and posts `{"userId":"U","groupId":"C"}` to `/memberships`.
Record `M3` belongs to another user and remains unchanged.
The framework reads and validates the complete record collection before issuing writes; it does not rely on the User object's current membership array.

[cols="1,3",options="header"]
|===
|Delta |Record operations
|Add |Create one record for each requested target absent from the current memberships.
|Remove |Delete every record belonging to this source and a requested target, using each record's identifier.
|Replace |Retain records for requested targets, delete records for other targets, and create records for missing targets.
|Clear |An empty replacement deletes every record belonging to this source.
|===

Repeated input values do not create duplicate memberships.
Existing duplicate records for a retained target remain unchanged; removing that target deletes all its records for this source.
The framework checks each record's source locally, including when the endpoint supports a source query filter.

=== Record configuration

`endpoint`::
  Required collection endpoint. Used for `GET` to read records and `POST` to create them.
  The optional `{source}` placeholder inserts the source UID as an encoded path segment, for example `/users/{source}/memberships`.

`sourceField`, `targetField`, `idField`::
  Required basic JSONPath expressions locating the source identifier, target identifier, and membership-record identifier in each record.
  Simple names such as `userId` and nested paths such as `$.relationship.userId` are supported.
  The source and target paths must identify structural object fields, not array elements or filtered paths, because they also define the JSON body for creation.
  The source value is the UID of the object being updated.
  Targets can be scalar identifiers or ConnId references containing the target UID.
  Configure native target identifiers; lookup mappings are not supported for these attributes.

`sourceType`, `targetType`::
  Identifier wire types: `string` (default) or `integer`.
  Set these to `integer` when the API expects JSON numbers instead of strings.
  For integer targets, returned membership changes use canonical decimal identifiers (for example, `0004` becomes `4`), preserving ConnId value types and reference metadata.

`deleteEndpoint`::
  Optional deletion endpoint; defaults to `endpoint` followed by `/{id}`.
  The `{id}` placeholder is the membership-record identifier, not the source or target identifier.
  `{source}` is also available for source-specific deletion paths.

`sourceParameter`::
  Optional query parameter receiving the source UID on each collection request, for example `sourceParameter "userId"`.
  This can reduce the response size; local source checks still apply.

`objectsPath`::
  Optional basic JSONPath locating the array in a response envelope, for example `objectsPath '$._embedded.elements'`.
  By default, the response itself must be an array.
  A missing collection path or malformed response is an error, not an empty membership list.

=== Pagination and failure behavior

Without pagination configuration, the collection endpoint must return every record in one response.
Pagination uses the shared `pagingSupport.parameters` YAML format and `pagingParameter` Groovy methods used by search endpoints.
For an API using record offsets, configure a positive page size and both `offset` and `pageSize` mappings:

[source,groovy]
----
relationshipRecords("groups") {
    endpoint "/memberships"
    sourceField "userId"
    targetField "groupId"
    idField "id"
    objectsPath '$.items'
    sourceParameter "userId"
    pageSize 100
    pagingParameter "offset", "query", "offset"
    pagingParameter "pageSize", "query", "limit"
    initialOffset 0
    maxPages 1000
}
----

The equivalent YAML pagination settings inside `update.relationshipRecords.groups` are:

[source,yaml]
----
objectsPath: $.items
sourceParameter: userId
pagingSupport:
  pageSize: 100
  parameters:
    offset: { in: query, name: offset }
    pageSize: { in: query, name: limit }
initialOffset: 0
maxPages: 1000
----

Both mappings are required when pagination is enabled; their names must match the remote API.
Use `in: header` (or `"header"` in Groovy) for APIs that accept pagination in HTTP headers.
Mappings must use distinct destinations and must not overwrite the source query parameter.
Body mappings and scripted paging are not supported for relationship collection GET requests.
`initialOffset` defaults to `0`.
The offset advances by the number of records returned, including records belonging to other sources.
The framework continues until an empty page, so a server returning fewer records than requested does not cause premature completion.
`maxPages` defaults to `1000` and bounds the scan, including its terminating empty page.
Repeated record identifiers across pages or reaching the page limit fail the update before any writes.
The endpoint must provide a stable offset-based traversal; cursor pagination and page-number pagination are not supported by this configuration.

Relationship handlers claim their configured attributes before ordinary REST endpoints and native SCIM update handlers.
An update may therefore combine membership changes with ordinary attribute changes without sending the membership array to the User endpoint.
The configuration applies to update deltas only: it does not create memberships when creating the parent, delete them when deleting the parent, or automatically populate membership attributes during search.
Configure these operations separately when needed.

Individual REST writes are not a transaction.
Collection reads must return HTTP `200` with the complete requested array or page.
Writes must complete synchronously: HTTP `202`, `206`, and `207` fail because the handler cannot poll for asynchronous completion or accept a partial result.
HTTP `404` while deleting a record found in the snapshot is accepted as already absent.
An HTTP failure is propagated, and successful earlier writes may remain applied.
Retrying the update reads the current membership records again.
Avoiding duplicates against concurrent writers requires the remote API to enforce uniqueness of the source/target pair; a read followed by a create cannot provide that guarantee by itself.

== Complex update script examples

=== Multiple endpoints needed for update

In some cases, the update operation may require multiple API calls to complete. For example, updating a `User` object may require updating basic information via a `PATCH` request to `/users/{id}` and updating additional attributes via a separate `PUT` request to `/users/{id}/attributes`.

The framework allows you to define multiple endpoints within the `update` block to handle such scenarios. Framework will select the appropriate endpoints to use based on the attributes being updated.

Attributes supported by each endpoint can be defined using `supportedAttributes` keyword.

[source,groovy]
----
objectClass("User") {
    update {
        endpoint("api/v3/users") {
            httpOperation PATCH
            supportedAttributes "admin", "email", "login", "password",
                    "firstName", "lastName", "status", "language"
            request {
                contentType APPLICATION_JSON
            }
        }
        endpoint("api/v3/users/{id}/attributes") {
            httpOperation PUT
            supportedAttributes "customAttribute1", "customAttribute2"
            request {
                contentType APPLICATION_JSON
            }
        }
    }
}
----

Where:
* This script heavily relies on default behavior of connector framework.
* The `update` block contains two `endpoint` definitions.
* Each `endpoint` specifies the API endpoint and HTTP operation to be used.
* The `supportedAttributes` keyword is used to define which attributes are handled by each endpoint.
** The framework will automatically determine which endpoints to call based on the attributes being updated in the request.
** Each endpoint can have its own `request` customization as needed.
** This approach allows for flexible handling of complex update scenarios involving multiple API calls.
** The default behavior of the connector framework is still leveraged for serialization and request handling.
* The `supportedAttribute(name) { value(...) }` block restricts the attribute to the listed value(s) — the endpoint is selected only when the delta values match.

NOTE: The `updateable` spelling is accepted as an alias of `updatable` in scripts.

=== Activation / locking attribute with separate endpoints

Some APIs provide dedicated endpoints for activating/deactivating or locking/unlocking objects. If the attribute used for activation / locking can not be updated directly in body of other attributes you may use `supportedAttribute` block, with also value specified to determine which endpoints will be used for switching that attribute value.

[source,groovy]
----
objectClass("User") {
    update {

        // Basic update ommited for clarity

        // Handles transition to active state
        endpoint(POST, "/user/{name}/activate") {
            supportedAttribute("active") {
                value true
            }
            request {
                body EMPTY
            }
        }
        // Handles transition to inactive state
        endpoint(POST, "api/v3/users/{id}/deactivate") {
            supportedAttribute("active") {
                value false
            }
            request {
                body EMPTY
            }
        }
    }
}
----

Where:

* This script heavily relies on default behavior of connector framework.
* The `update` block contains two `endpoint` definitions for handling activation and deactivation.
* Each `endpoint` specifies the API endpoint and HTTP operation to be used.
* The `supportedAttribute` block is used to define which attribute and value triggers the use of each endpoint.
** The framework will automatically determine which endpoint to call based on the value of the `active` attribute in the update request.

The same activation endpoint in YAML:

[source,yaml]
----
objectClasses:
  User:
    update:
      endpoints:
        - method: POST
          path: /user/{name}/activate
          request:
            body: EMPTY
          supportedAttributes:
            - name: active
              value: true
----
