= Declarative YAML

The SCIMREST framework supports a declarative YAML form for schema definitions, operation handlers, and authentication, in addition to (and instead of) Groovy scripts.

YAML documents and Groovy scripts are two front-ends over the *same* builders — a YAML document drives the same live builders the Groovy DSL does, so both forms can be mixed per connector and a connector can migrate a script to YAML without changing the manifest.

This document is part of the SCIMREST connector tutorial. See the framework introduction for other topics.

== Groovy to YAML fallback

The loader resolves each manifest script resource with a YAML fallback: when the referenced `.groovy` file is missing from the bundle, a `.yaml` / `.yml` file with the same base name is loaded instead.

Parsing is strict: a file must contain exactly one document, and unknown keys fail fast.

== Schema documents

A YAML schema document describes object classes under the `objectClasses` root (one entry per object class; a file may describe several classes). Documents naming the same object class merge into one definition, so a native definition and a ConnId overlay can stay in separate files.

[source,yaml]
----
objectClasses:
  User:
    # SCIM-specific mapping for the whole object class
    scim:
      extensions:
        enterprise: "urn:ietf:params:scim:schemas:extension:enterprise:2.0:User"
    attributes:
      givenName:
        scim:
          path: name.givenName
      primaryEmail:
        scim:
          path: emails[primary eq true].value
      employeeNumber:
        scim:
          path: urn:ietf:params:scim:schemas:extension:enterprise:2.0:User:employeeNumber
  Office:
    attributes:
      name:
        connId:
          name: NAME
----

The `scim.extensions` mapping binds each extension alias to its SCIM schema URI (or to a mapping with a required `uri` and an optional `flatten` list).

Keys:

`objectClasses.<name>`::
  One object class (the counterpart of `objectClass("...") { ... }`)

`description` / `embedded`::
  The corresponding object-class flags

`connId` (object-class level)::
  Built-in attribute aliases, e.g. `connId: { UID: user_id }` binds `__UID__` to the `user_id` attribute

`scim` (object-class level)::
  `schemaUri`, `name` (the SCIM resource name), `onlyExplicitlyListed`, `flatten` (a list of complex attribute names to flatten, or a single name), and `extensions` (alias → SCIM schema URI, or a mapping with a required `uri` and an optional `flatten` list)

`attributes.<name>`::
  One attribute — see the attribute keys below

`references.<name>`::
  A reference attribute (memberships, foreign keys): `objectClass`, `role` (`subject` / `object`), `subtype`

(`relationships` is not available in YAML — declare associations in a Groovy schema script; see the REST relationship topic.)

Attribute keys (all optional — only present keys are applied, so the defaults stay untouched):

`description`, `required`, `multiValued`, `creatable`, `updateable` / `updatable`, `readable`, `returnedByDefault`, `emulated`::
  The regular attribute settings (see user schema)

`jsonType`, `openApiFormat`, `complexType`::
  JSON wire type, OpenAPI format, and the embedded object class for structured attributes

`json: { name, type, openApiFormat, path, implementation }`::
  The JSON wire mapping block; `path` maps the attribute to a (nested) JSON location — see the attribute paths below. `implementation` is a block with `deserialize` and/or `serialize` Groovy fragments — the declarative counterpart of the Groovy DSL `json { implementation { deserialize { … } serialize { … } } }`; the fragment receives the wire value as `value` (deserialize) / the ConnId value as `value` (serialize) and must return the converted value. A fragment may carry its own `import` lines as its leading lines — they are hoisted out of the compiled closure, so `new ConnectorObjectReference(...)` and friends work without any implicit imports. Key order within the block is free: `type` / `openApiFormat` are resolved lazily, so `implementation` may come before or after them

`connId: { name, type }`::
  The ConnId-side name (including the `__UID__` / `__NAME__` built-ins) and value type — a capitalized, case-sensitive Java type name (`String`, `Integer`, `Long`, `Boolean`, `Double`, `BigDecimal`, `Binary`, `GuardedString`, …)

`scim: { name, type, path }`::
  The SCIM wire name, SCIM type, and SCIM attribute path (a path string such as `name.givenName`, `emails[0].value`, `emails[primary eq true].value`, or a full extension URI) — see the attribute paths below

(Custom SCIM value mapping — `scim { implementation { deserialize { … } serialize { … } } }` — is Groovy-only and is not available in YAML.)

A bare `attr:` (no keys) declares the attribute with defaults — the counterpart of `attribute("x")` with an empty closure.

=== Attribute paths

The `path` key of the `json:` and `scim:` blocks maps the attribute to a (nested) wire location. A scalar uses the block's default format: `json.path` is a basic JSONPath expression (`$.name.givenName`, `$.emails[?(@.primary == true)].value`) and `scim.path` is a SCIM attribute path (`name.givenName`, `emails[primary eq true].value`, or a full extension URI). An explicit format is supported via a `{ type, value }` mapping (the `type` is case-insensitive):

[source,yaml]
----
attributes:
  primaryEmail:
    json:
      path:
        type: JSON_POINTER   # JSON_PATH | JSON_POINTER
        value: /emails/0/value
----

The counterpart of the Groovy `json { path { type JSON_POINTER; value "/emails/0/value" } }` / `scim { path "..." }` DSL. The expression is parsed lazily, so an invalid expression fails at schema build time with the file location.

The YAML schema is fully literal: the builder deliberately gets no runtime context, so context-dependent Groovy fails fast at load time.

== Operation documents

An operation document covers one or more of `search`, `create`, `update`, or `delete` per object class, under the same `objectClasses` root; a top-level `authentication` block may be added in the same file. One file may carry several object classes.

=== Search

[source,yaml]
----
objectClasses:
  User:
    search:
      endpoints:
         - path: /users/search
           method: POST
           responseFormat: JSON_OBJECT
           emptyFilterSupported: true
           objectExtractor:
             value: $.users
           # objectsPath: $.users                      # the same, as the plain path form
           # objectExtractor: |
           #   response.body().get("users")  # Groovy alternative for arbitrary logic
           pagingSupport:
             parameters:
               pageSize:
                 in: query
                 name: size
               page:
                 in: query
           # pagingSupport: |
           #   request.queryParameter("size", paging.pageSize)  # Groovy alternative
           request:
             queryParameters:            # static query parameters sent with every request
               jql: created >= 1970-01-01 ORDER BY created ASC   # (e.g. a fixed JQL on JIRA's search/jql endpoint)
               fields: summary,status,project,created
             # contentType: APPLICATION_JSON  # Content-Type of the (usually POST) request body
           supportedFilters:
            - spec: attribute("login").eq().anySingleValue()
              request: |
                request.queryParameter("login", value)
         - path: /users/{id}
           singleResult: true
           supportedFilters:
             - spec: attribute("id").eq().anySingleValue()
               request: |
                 request.pathParameter("id", value)
         - path: /users/disabled   # concrete-value filter: the endpoint serves the filter itself
           supportedFilters:
             - spec: attribute("enabled").eq(false)   # no request block - the search is routed here as-is
      attributeResolvers:
        - attribute: team
          resolutionType: PER_OBJECT
          implementation: |
            # Resolve the team attribute for each result object
      custom:
        emptyFilterSupported: true
        supportedFilters:
          - spec: attribute("login").eq().anySingleValue()
        implementation: |
          # Custom search logic — see the custom search guide
----

`search.endpoints[].path`::
  The search / list endpoint path (required)

`search.endpoints[].method`::
  The HTTP method of the search endpoint: `GET` (default) or `POST` — for APIs that search via a POST request with a (form or JSON) body

`search.endpoints[].responseFormat`::
  Whether the response is a JSON array or a JSON object: `JSON_ARRAY` / `JSON_OBJECT`; default `JSON_OBJECT`

`search.endpoints[].objectExtractor`::
  How the list of objects is extracted from the response, in one of two forms. A *path mapping* `{ type, value }` (the same `{ type, value }` shape as the attribute `path` keys) resolves a JSON Pointer (`/_embedded/elements`) or a basic JSONPath (`$._embedded.elements`) against the response body — a resolved array yields its elements, a resolved object yields the single object, and a missing path yields no objects; `type` is case-insensitive and defaults to `JSON_PATH` (so `value:` alone is a JSONPath expression). A *string or block scalar* (plain or `|`) is compiled as a *Groovy closure* with the variable `response` — so `objectExtractor: $.data` is Groovy code, not a JSONPath expression (in the Groovy DSL, `objectExtractor("…")` with a plain string is a path expression instead). For a plain path, use `objectsPath` instead. The default (no `objectExtractor`) handles a JSON array or a single object

`search.endpoints[].objectsPath`::
  The path to the list of objects in the response — the unambiguous path form of `objectExtractor`: a scalar is a basic JSONPath expression (`$._embedded.elements`) and a `{ type, value }` mapping selects an explicit format (`JSON_PATH` or `JSON_POINTER`, case-insensitive, default `JSON_PATH`) — the same shape as the attribute `path` keys. A resolved array yields its elements, a resolved object yields the single object, a missing path yields no objects. Groovy counterpart: `objectsPath("$._embedded.elements")` (or with an explicit `AttributePathDeclaration`)

`search.endpoints[].pagingSupport`::
  How paging information is mapped onto the request, in one of two forms. A *mapping* declares the paging declaratively: `pageSize` (the requested page size, default 25) and/or `parameters` — a mapping of paging tokens to where they are sent. Each token entry takes `in` — `query`, `header`, or `body` (a request body; requires `method: POST`) — and an optional `name` (the request parameter name, defaulting to the token). The tokens are `pageSize` (the requested page size), `page` (the page number, starting with 1), and `offset` (the zero-based object offset, `(page - 1) * pageSize`). Example: `parameters: { pageSize: { in: query, name: size }, page: { in: query } }`. A *Groovy block* (variables `request`, `paging` with `pageSize` and `pageOffset`) keeps arbitrary mapping logic. The two forms are mutually exclusive; `pageSize` alone (without `parameters`) composes with the Groovy form by feeding its `paging.pageSize`

`search.endpoints[].request`::
  Customizes every request the endpoint issues (the YAML counterpart of the Groovy `request { ... }` block)

`search.endpoints[].request.queryParameters`::
  A mapping of query parameter name to scalar value — added to the query string of every request the endpoint issues (e.g. a fixed `jql` / `fields` on a JIRA-style `search/jql` endpoint); a `null` entry adds nothing

`search.endpoints[].request.contentType`::
  The Content-Type of the (usually POST) search request body — a literal media type (`application/json`) or one of the built-in constant names (`APPLICATION_JSON`, `APPLICATION_XML`, `APPLICATION_YAML`, `APPLICATION_HAL_JSON`)

`search.endpoints[].singleResult`::
  The endpoint returns exactly one object

`search.endpoints[].emptyFilterSupported`::
  The endpoint supports the empty (list-all) filter

`search.endpoints[].supportedFilters[].spec`::
  A filter specification as a build-time Groovy expression, e.g. `attribute("id").eq().anySingleValue()` (see the filter specification API)

`search.endpoints[].supportedFilters[].request`::
  Optional Groovy block mapping the filter onto the request (variables `request`, `value`). When omitted, the entry declares a concrete-value filter the endpoint serves on its own: a search whose filter matches the `spec` is routed to the endpoint with the request left unmodified (e.g. `spec: attribute("enabled").eq(false)` on a `users/disabled` endpoint that already returns only the disabled users)

`search.normalize`::
  UID/NAME rewriting for reference attributes: `toSingleValue` (attribute name) plus the `rewriteUid`, `rewriteName`, `restoreUid`, `restoreName` Groovy blocks (variables `original`, `value`)

`search.attributeResolvers[]`::
  One resolver per entry: `attribute`, `resolutionType` (`PER_OBJECT` / `BATCH`), and the `implementation` Groovy block

`search.custom`::
  Custom search: `supportedFilters` (each a `spec` expression), `emptyFilterSupported`, and the `implementation` Groovy block (see custom search)

=== Create / update / delete

[source,yaml]
----
objectClasses:
  User:
    create:
      endpoints:
        - method: POST
          path: users
          request:
            contentType: application/json
    update:
      endpoints:
        - method: PATCH
          path: /users/{id}
          request:
            contentType: application/json
          supportedAttributes:
            - firstName
            - lastName
            - email
         # Dedicated endpoint — no body required
         # (the transition filter is accepted but not enforced yet)
        - method: POST
          path: /users/{id}/lock
          request:
            body: EMPTY
          supportedAttributes:
            - name: status
              transition:
                from: active
                to: locked
    delete:
      endpoints:
        - method: DELETE
          path: /users/{id}
----

`enabled`::
  Per-operation switch, e.g. `create: { enabled: false }`

`endpoints[].method`::
  HTTP method (`POST`, `PUT`, `PATCH`, `DELETE`, ...); default `POST`

`endpoints[].path`::
  The endpoint path (required); `{name}` path parameters are replaced from the object

`endpoints[].request.contentType`::
  The request content type — a literal media type (`application/json`) or one of the built-in
  constant names (`APPLICATION_JSON`, `APPLICATION_XML`, `APPLICATION_YAML`, `APPLICATION_HAL_JSON`),
  which resolve to the corresponding media type the same way as in the Groovy DSL

`endpoints[].request.body`::
  `EMPTY` for no body; the default serializes the supported `creatable` / `updateable` attributes into a JSON body. (A custom Groovy body block is not supported for create/update/delete — the body is built from the supported attributes.)

`endpoints[].request.queryParameters`::
  A mapping of query parameter name to scalar value — added to the query string of every request the endpoint issues; a `null` entry adds nothing

`endpoints[].supportedAttributes`::
  Plain attribute names, a fixed value (`{ name, value }`), or a value transition (`{ name, transition: { from, to } }` — accepted but not enforced yet; a transition-only entry matches no requests)

See create, update, and delete for the operation semantics.

== Authentication

An `authentication` block (top-level, not per object class) configures the authentication methods of the `rest` and/or `scim` namespace:

[source,yaml]
----
authentication:
  rest:
    bearer:
      implementation: |
        request.header("Authorization", "token " + decrypt(configuration.restTokenValue))
    apiKey:
      implementation: |
        request.header("Authorization", "token " + decrypt(configuration.restTokenValue))
    preference:
      - bearer
      - apiKey
----

`authentication.rest` / `authentication.scim`::
  The per-namespace channel blocks

`apiKey`, `basic`, `bearer`, `jwtBearer`::
  Each accepts an `implementation` Groovy block that customizes the request

`oauth2ClientCredentials`, `oauth2JwtBearer`, `oauth2Password`, `oauth2Saml`::
  The OAuth 2.0 flavors; each accepts the hooks `buildTokenRequest`, `parseTokenResponse`, `validateToken`, `applyToken`, `onResponse` (Groovy blocks) and an `implementation` block

`preference`::
  Ordered list of method names (`apiKey`, `basic`, `bearer`, `jwtBearer`, the `oauth2*` flavors, `awsSignature`)

See authentication & authorization for the properties each method consumes.
